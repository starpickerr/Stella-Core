# Stella 智能简报系统优化设计方案

> 文档性质：产品与交互设计方案
>
> 适用范围：Stella 桌面端简报、邮箱/eLearning 来源、事务、日程、自动化及 Agent 联动
>
> 非目标：本方案不规定数据库表、接口协议或具体技术架构。文中“事项”“变化”“处理记录”等是产品概念，用于约束后续实现和验收。

## 1. 设计结论

### 1.1 产品定位

简报从“把邮件写成一段摘要”升级为 **Stella 的变化驱动信息中心**：

1. 识别自上次简报以来真正发生的变化，并将同一事项连续追踪。
2. 先告诉用户“发生了什么”，再告诉用户“Stella 已经做了什么”，最后明确“用户还要决定或完成什么”。
3. 只引用事务、日程、账单等业务模块的真实状态；简报不再维护一套平行的任务状态。
4. 把来源事实、Agent 判断、Stella 实际操作结果分开呈现，用户可以核查每一个结论。

简报的职责是整合、解释变化和引导行动。事务、日程、账单、自动化仍是各自业务对象的管理入口。

### 1.2 现有能力评估

Stella 已有一条可复用的纵向链路：

- 邮箱和 eLearning 通过 `source_items` 统一进入来源目录，保留账号、来源 ID、线程、时间、原文链接和正文快照。
- `BriefingPipeline` 按每个来源维护成功同步边界，支持候选、精选、过滤、失败来源保留旧内容和部分成功。
- Agent 对候选逐项判断是否精选、生成理由、摘要、`action/fyi` 分类及分数；正文和卡片已经分开存储。
- 同一线程可合并成一张卡，历史版本保存正文、卡片及来源分类，用户可以查看旧版本。
- 简报版本通过 outbox 投影到日程和事务；事务以来源键更新，用户手动修改后不会被简报覆盖；日程保留用户修改记录。
- Scheduler 已能静默调用 `briefing`，并拥有失败重试、当天补执行等能力；手动生成和定时生成最终进入同一条 Pipeline。
- 页面已有历史列表、今日生成/更新、正文、条目状态选择、候选/精选/过滤统计、来源设置和版本时间线。

这些能力解决了“能拉取、能筛选、能保存、能投影”的基础问题，但当前产品表达仍有六个断点：

1. 正文和卡片都承担摘要职责，同一信息在概览、卡片和详情重复出现。
2. `action/fyi` 是二元分类，无法表达“状态更新”和“普通动态”；分数缺少可理解的优先级解释。
3. 条目状态（`undo/done/follow_up/ignored`）同时被用户理解成已读、已处理和业务完成，无法表达自动处理失败或业务对象的真实状态。
4. 线程合并和来源键解决单次生成的重复，但没有形成跨简报的“同一事项”与“发生变化”视图，未变化事项可能反复出现。
5. 日程、事务投影已经发生，但卡片没有统一显示操作是否成功、目标对象是什么、失败原因是什么。
6. 手动更新与定时简报共享流程，却没有向用户解释“本次只看新增变化”还是“查看所有仍未解决事项”。

### 1.3 关键取舍

- **分类与优先级分离**：分类回答“这是什么信息”，优先级回答“现在有多重要”。不使用一个分数替代两者。
- **事项优先于消息**：多封邮件和课程记录可以指向一个持续事项；用户看到的是事项的变化，详情中仍可核查所有来源。
- **结果优先于意图**：Agent 说“已创建事务”不等于事务真的创建；只有业务模块返回成功才显示“已执行”。
- **渐进呈现**：首屏只给决策所需信息，完整正文、原始来源、历史和操作日志按需展开。
- **保守自动化**：高置信、低风险、符合授权的同步可以自动执行；创建、改期、外部发送等有影响的动作默认建议或确认。

## 2. 信息模型与内容契约

### 2.1 四类信息

四类是互斥的当前展示分类，但可以随事项变化而重新分类。分类不表示用户是否已经读过，也不表示关联事务是否完成。

| 分类 | 解释 | 典型内容 | 默认用户期待 |
| --- | --- | --- | --- |
| **需要行动** | 用户需要完成、确认或做决定，存在明确下一步 | 作业未完成、待审批、需要回复、需要确认改期 | 首屏优先，给出一个主操作 |
| **值得关注** | 影响或风险较高，暂时不一定需要立即操作 | 成绩异常、费用异常、重要政策变化、连续失败 | 显示原因和关注期限，可转事务 |
| **状态更新** | 已存在事项或业务对象的事实状态发生变化 | 已提交、已评分、截止日期调整、事务进入阻塞 | 说明变化前后，引用真实业务状态 |
| **其他动态** | 低风险、低紧迫的普通通知或资料变化 | 资料更新、竞赛资讯、一般公告 | 收起或低频展示，不自动生成事务 |

分类规则：

- 有明确用户动作且动作未完成时优先归入“需要行动”。
- 没有动作但对成绩、费用、时间安排或权限有显著影响时归入“值得关注”。
- 已关联业务对象且本次只是状态变化时归入“状态更新”，即使该变化最终要求用户知悉。
- 其余信息进入“其他动态”；用户可以在偏好中降低或关闭该类展示。
- 同一事项同一简报只出现一次；若同时有“截止日期变化”和“需要确认”，以需要行动为主分类，并在卡片显示“截止日期变化”变化标签。

旧版迁移映射：旧 `action` 默认进入“需要行动”；旧 `fyi` 由规则和变化类型重新判断，不能全部映射为“其他动态”。旧 `done` 只保留为“用户已处理”的历史处理记录，不推断业务对象已完成。

### 2.2 优先级体系

优先级与分类独立，首期使用三个可理解等级，不在主界面显示 0–100 分：

| 优先级 | 显示 | 进入首屏的条件 | 示例 |
| --- | --- | --- | --- |
| P0 | 立即关注 | 已逾期、极短截止、重大影响且高置信，或自动处理失败造成遗漏风险 | 今日 18:00 前必须确认的审批 |
| P1 | 重要 | 未来数日截止、影响成绩/财务/行程，或状态出现异常 | 成绩异常、作业截止日提前 |
| P2 | 常规 | 有价值但可稍后处理，或仅供了解 | 课程资料更新、一般活动通知 |

优先级由以下因素共同决定，并在详情中解释触发原因：

1. 紧急程度：截止时间、逾期时长、时间窗口。
2. 影响程度：对学习、财务、行程、承诺或用户明确目标的影响。
3. 变化幅度：新事项、关键字段变化、异常或连续失败比无变化更重要。
4. 用户偏好：来源、课程、联系人、类别和免打扰时段。
5. 信息可信度：来源明确程度、字段完整性和 Agent 置信度。

卡片最多展示两个可读原因，例如“明日截止 · 影响课程成绩”“截止日提前 2 天 · 来源已确认”。AI 低置信时降级为 P2 或进入“待确认”，不能用推测日期制造 P0/P1。

### 2.3 事项、来源与变化

产品上引入一个持续的“事项”概念，但不把它做成新的业务管理模块：

- **事项**：用户关心的持续主题，例如“数据结构作业 2”。
- **来源事件**：邮件、课程作业、评分记录等具体事实。
- **业务引用**：事务、日程、账单或自动化中的真实对象 ID和当前状态。
- **变化**：与上一次已见事实相比的新建、字段修改、状态转移、异常或临近截止。

事项卡片展示最新状态和变化；详情展示来源事件列表和时间线。没有可靠的事项归并依据时，宁可保留为两件事项，也不强行合并。

## 3. 简报生成与内容逻辑

### 3.1 生成步骤

每次生成遵循同一条产品流程：

1. **读取窗口**：读取上次成功同步边界之后的新来源，同时检查仍未解决的 P0/P1 事项和自动操作失败。
2. **归并事项**：按来源稳定标识、线程、课程/作业/账单等业务键进行候选归并。
3. **识别变化**：标记新事项、重要变化、持续关注、已解决和无变化。
4. **事实核验**：记录来源确认的字段；缺失或冲突字段标为未知，禁止 Agent 补猜。
5. **分类与排序**：先分类，再计算优先级，最后按用户偏好和截止时间排序。
6. **执行联动**：按授权等级执行或提出建议，等待业务模块返回实际结果。
7. **生成简报**：先生成概览，再生成卡片；卡片只引用已核验的最新状态。
8. **保存版本**：保存本次窗口、生成触发方式、来源分类和处理结果，供后续比较。

失败时保留上一份成功简报和已确认的业务状态；本次失败、未覆盖的来源和重试入口必须显式显示。

### 3.2 概览摘要

概览只回答三件事，建议控制在 3–5 行或 3 个短段落：

- **发生了什么**：例如“新增 2 个事项，1 个截止日期提前，1 个作业已评分”。
- **Stella 已处理什么**：例如“已更新 1 个事务和 1 条提醒；日程同步成功”。
- **还需要什么**：例如“有 2 项需要你确认，其中 1 项明日截止”。

概览附带：简报生成时间、覆盖窗口、来源成功/失败数、重要信息数、未解决 P0/P1 数。概览不逐项复述卡片标题，不展示完整邮件段落；点击数量或短语直接筛选卡片。

当没有新变化但仍有重要未解决事项时，概览明确写“本次没有新来源，仍有 1 项临近截止”，避免空白页面或伪造新消息。

### 3.3 卡片内容契约

卡片默认只展示：

1. 分类、优先级和变化标签。
2. 标题和一句关键变化（不超过两行）。
3. 截止时间或业务状态（来自真实模块）。
4. Stella 处理结果摘要和用户下一步。
5. 一个主操作、一个次操作及“更多”菜单。

建议卡片字段示例：

> **需要行动 · P1**　截止日期提前 2 天
>
> 数据结构作业 2　—　现截止 10 月 12 日 23:59
>
> Stella 已更新事务和截止提醒；尚未提交作业。　[打开事务] [查看来源]

主操作必须与分类一致：需要行动优先打开事务/确认，值得关注优先查看详情/加入关注，状态更新优先查看业务对象，其他动态优先打开来源。卡片不直接塞入整封邮件正文。

### 3.4 详情内容

点击卡片展开抽屉或详情页，按以下顺序展示：

1. **事实**：来源、时间、原文关键字段和可验证链接。
2. **变化**：上次值→本次值，或“首次出现”；没有对比依据时写明“暂无历史值”。
3. **AI 分析**：分类、优先级、置信度、理由和建议，明确标注“AI 判断”。
4. **自动处理**：每个动作的授权依据、执行时间、目标业务对象、实际返回结果和失败原因。
5. **业务关联**：事务、日程、账单等对象的链接及当前状态，显示“由事务模块维护”。
6. **来源与历史**：关联邮件/课程记录、线程、原文、跨简报时间线。
7. **可用操作**：查看事务、查看日程、确认、重试、建议创建事务、打开原文、忽略本事项。

详情中的完整正文、过滤理由和候选邮件继续保留，但默认折叠在“来源详情”下；历史版本只读。

## 4. 页面与交互设计

### 4.1 简报首页布局

保持 Stella 现有桌面端设计语言、圆角卡片、低干扰背景和紧凑间距，页面结构调整为：

```text
┌ 左侧：日期/运行历史 ┐ ┌ 主区：今日简报                         ┐
│ 今天                 │ │ [时间] [覆盖窗口] [刷新] [完整概览]     │
│ 10 月 7 日  · 3 项   │ │ 发生了什么 · Stella 做了什么 · 需要什么 │
│ 10 月 6 日  · 1 项   │ │ [需行动] [值得关注] [状态更新] [其他]    │
│ …                    │ │ 紧急卡片                               │
│                      │ │ 其他卡片（可折叠）                      │
└──────────────────────┘ └───────────────────────────────────────┘
```

- 左侧历史显示日期、状态、P0/P1 数量和未处理数，不再只显示精选总数。
- 主区优先显示“需要行动”和 P0/P1；“其他动态”默认折叠。
- 顶部筛选支持“全部变化 / 仅新变化 / 仍未解决 / 来源”，筛选不改变事项状态。
- “查看完整当前概览”是手动模式，只读当前未解决事项和近期状态，不生成新的事项、不重复执行联动。
- 移动窄屏沿用现有返回交互，先展示概览和卡片，再进入详情。

### 4.2 卡片交互

- 点击卡片主体展开详情；点击主操作直接进入对应业务模块，成功返回后卡片即时刷新。
- “已读”是轻量操作，不替代“确认”“完成”或“忽略”。进入详情可以自动标为已读，但不改变处理状态。
- 用户选择“忽略”时允许选择“一次忽略”或“此事项后续无变化不再提醒”；出现新截止、异常或状态变化时仍可重新提醒。
- 对低置信判断显示“需要确认”按钮，用户确认后才执行有副作用操作。
- 操作失败显示原因和“重试”；若结果未知，显示“结果待核对”，提供查看业务对象和重新核对，不显示成功徽章。

### 4.3 生成中的反馈

继续复用现有草稿进度，但文案改为用户可理解的阶段：

1. 正在读取来源（显示已完成/总来源和失败来源）。
2. 正在识别变化（显示候选事项数，不展示模型内部思考）。
3. 正在同步业务（显示待确认、成功、失败数量）。
4. 正在整理简报。

草稿只作为预览；直到保存成功和业务结果返回，卡片不能宣称自动操作完成。

### 4.4 设置与关注偏好

在现有来源管理和规则文稿之外增加“简报偏好”分组：

- 每类信息的显示级别：正常、仅 P0/P1、关闭。
- 来源/课程/联系人关注：关注、普通、静音。
- 关注频率：每次变化、每日一次、仅截止前提醒。
- 免打扰时段和临近截止提前量。
- 自动联动授权：只更新已有事务；允许创建事务；允许创建日程；所有高风险动作始终确认。
- 默认生成方式：定时简报看“新增变化”，手动简报默认看“自上次简报以来的变化”；用户可切换“完整当前概览”。

规则文稿继续负责语义筛选和写作风格，偏好面板负责稳定的频率、来源和授权选择；两者不重复配置。

## 5. 三套状态必须分开

### 5.1 信息状态

只表示用户是否看过来源或卡片：

- 未读
- 已读
- 已归档

信息状态不会改变事务、日程或账单，也不会把一封邮件标为已完成。

### 5.2 处理状态

表示 Stella 对该事项建议或执行的动作：

- **无需操作**：仅供了解，或用户已选择不处理。
- **待确认**：存在风险、权限不足或置信度不足，等待用户授权。
- **待执行**：已确定动作但尚未开始，例如等待重试队列。
- **执行中**：业务模块正在处理。
- **已执行**：业务模块返回成功，并保存目标对象和时间。
- **执行失败**：明确失败，显示原因和重试/改用手动操作入口。
- **结果待核对**：请求超时或返回不确定，禁止当作成功。

一个事项可以有多个处理动作，例如事务更新成功但提醒同步失败；卡片显示聚合状态，详情逐项展示结果。

### 5.3 业务状态

由事务、日程、账单或来源模块维护，简报只读取和链接：

- 事务使用现有 `todo/in_progress/waiting/blocked/completed/cancelled`。
- 日程使用真实事件、时间和用户修改标记。
- eLearning 保留来源确认的“未提交/已提交/已评分”等状态。
- 账单使用账本或账单模块的实际状态。

示例：一项已评分作业可以是“简报未读 + eLearning 同步已执行 + 关联事务 completed”。简报不能因为用户读过卡片就把作业变成完成，也不能把“已评分”改写成“已提交”。

### 5.4 事实、推断、结果的视觉表达

详情使用三个固定区块和标签：

- **来源事实**：带来源图标和原文链接，使用“来源确认”。
- **AI 判断**：分类、优先级、相似事项、建议，使用“AI 判断 · 置信度高/中/低”。
- **Stella 结果**：业务模块返回的成功、失败、待核对，使用“已执行/执行失败”。

三者不得合并为一句没有证据的“已处理”。

## 6. 跨模块协同

### 6.1 作业通知

1. 识别课程、作业身份和截止时间，关联已有同一作业事项。
2. 若已有事务，默认更新标题、来源链接和截止时间；保留用户修改字段并提示冲突。
3. 若没有事务：高置信且用户已授权“允许创建事务”时自动创建；否则显示“建议创建事务”。
4. 明确截止时间进入事务的 `due_on/due_time`，提醒由事务模块管理。
5. 卡片显示事务真实状态和提醒同步结果，不显示简报自己的待办状态。

### 6.2 已提交、已评分通知

- “已提交”只更新 eLearning 业务状态为已提交，并将关联事务转为“等待/进行中”或保留用户当前状态，具体映射需遵循用户规则。
- “已评分”只更新评分和成绩信息；若作业要求用户查看反馈或修订，仍可为“需要行动”。
- 只有来源或用户明确确认完成时，才把事务置为 `completed`；评分本身不等于用户完成全部后续工作。
- 状态更新卡保留前后值和时间，避免连续简报只写“有新邮件”。

### 6.3 截止日期变化

1. 对比事项历史中的旧截止时间和新截止时间。
2. 同步事务截止日期及其提醒；事务被用户手动改过时先标记冲突并请求确认。
3. 日程若由该来源生成且未被用户修改，则同步；用户修改的日程保留并提示差异。
4. 截止提前、逾期或距离阈值内时重新提醒；仅格式变化不重复提醒。

### 6.4 普通资讯

资讯默认归入“其他动态”，不自动创建事务。满足以下条件时才提供“建议加入事务”：用户明确关注、存在明确截止/承诺、影响较大且信息可信。建议进入待确认，不直接写入事务库。

### 6.5 日程、事务与账单

- 有明确会议/活动时间的来源可以建议或创建日程；行动条目的截止时间优先交给事务提醒，避免同时生成重复日程。
- 费用通知只有在来源字段足够完整且用户授权时，才建议进入账单模块；普通促销和支付成功通知不自动成为账单记录。
- 所有投影以来源稳定键幂等更新；用户在目标模块手动改动后，简报展示冲突而不覆盖。

### 6.6 自动化与每日简报

- 每日定时任务只负责触发一次简报生成，不复制来源读取和事项逻辑。
- 定时模式默认覆盖“上次成功简报之后的新变化 + 仍需关注的 P0/P1/失败动作”。
- 手动“生成/更新”默认同样突出新增变化；“完整当前概览”只读，不推进来源边界、不再次执行已成功动作。
- 错过定时执行时使用 Scheduler 的当天补执行语义；不得为离线的每一天重复生成多份简报。
- 生成失败、来源部分失败和投影失败分别显示，重试只重试对应阶段，避免重新执行已成功的外部动作。

## 7. 去重、变化追踪与延迟数据

### 7.1 事项身份优先级

按可靠性从高到低使用以下依据：

1. 来源账号 + 来源原生 ID。
2. 线程 ID或课程/作业、账单等业务对象标识。
3. 标题、发件人、课程和时间的语义匹配。

语义匹配只能提出候选关系；低置信或存在冲突时分开显示并提示“可能是同一事项”。来源账号必须参与身份判断，避免两个邮箱相同 Message-ID 互相覆盖。

### 7.2 变化类型与展示策略

每次事项变化标记为：

- **新发生**：首次见到或尚无历史快照。
- **重要变化**：截止、状态、金额、时间、权限或异常字段改变。
- **持续关注**：没有新来源，但仍处于 P0/P1、逾期、阻塞或自动处理失败。
- **已解决**：业务对象已完成、取消或用户明确关闭；默认只在一次状态更新中出现。
- **无重要变化**：仅正文、格式或重复通知变化；不进入首屏。

连续简报中同一事项没有重要变化时，不重复生成卡片。用户仍可从“当前事项”查看它；被用户忽略的事项只在有重要变化时重新出现。

### 7.3 跨简报抑制与重新提醒

- 已读不等于已解决；“已读但未完成”的需要行动事项仍可作为持续关注显示。
- 用户选择“本次忽略”只抑制当前简报；选择“无变化不再提醒”才建立持续抑制。
- 截止临近、截止调整、状态异常、优先级升级、处理失败和来源补齐会解除抑制。
- 同一事项每日最多一次主动提醒；P0 发生新变化可突破频率限制，并显示突破原因。

### 7.4 延迟获取与窗口边界

来源同步边界与信息发生时间分开处理：

- 每个来源保留“已成功读取到哪里”和“这条信息实际发生时间”两个概念。
- 首次迟到的邮件、延迟评分或接口恢复后补齐的数据，即使发生时间早于窗口结束，只要此前未见且在来源同步中首次确认，就进入“延迟到达”变化。
- 已见来源的正文补齐或格式更新不重新提醒，除非关键字段发生变化。
- 来源部分失败时不推进该来源边界；简报显示覆盖不完整和重试入口，不能把“没有读到”当成“没有变化”。
- 手动完整概览读取当前事项，不受本次增量窗口限制，但不伪造一个新的时间窗口。

## 8. 典型使用场景

### 场景一：收到新作业通知

1. 来源确认课程、作业和截止时间，事项识别为新发生、P1、需要行动。
2. 用户已授权自动建事务，Stella 创建事务并同步截止提醒；两项都返回成功。
3. 概览写“新增 1 项作业，事务和提醒已创建”；卡片只写关键变化和截止时间。
4. 用户点“打开事务”完成后，事务页改变真实状态；返回简报时卡片显示业务状态，不依赖卡片下拉框。

### 场景二：作业已提交但尚未评分

1. eLearning 来源确认提交状态，归入状态更新，P2 或按用户偏好升级为 P1。
2. 事务保留“等待/进行中”或用户已有状态，不直接标记完成。
3. 卡片显示“已提交 · 等待评分”，详情展示提交时间和来源链接。
4. 后续没有新变化时不重复出现；评分到达时以状态变化重新出现。

### 场景三：截止日期提前

1. 同一事项收到新截止日期，识别为重要变化，升级为 P1。
2. Stella 更新未被用户修改的事务和提醒；日程按权限同步。
3. 若事务曾被用户改期，显示“来源截止日与事务日期冲突”，处理状态为待确认。
4. 用户确认后才覆盖用户字段；所有变更保留前后值。

### 场景四：普通课程资料更新

1. 信息归入其他动态，P2，默认不创建事务。
2. 用户对该课程设置了高关注，卡片提升到值得关注但仍不自动建事务。
3. 用户点击“加入事务”后才进入事务创建确认，确认结果和事务 ID在详情中可见。

### 场景五：自动同步失败

1. 来源已读取邮件，但事务写入超时；信息事实仍可展示。
2. 卡片分开显示“来源已收到”和“事务同步失败”，处理状态为执行失败或结果待核对。
3. 用户可点击重试；重试只调用事务投影，不重新处理邮件，也不产生重复事务。
4. 直到业务模块确认成功，概览都把该失败列入“需要关注”。

### 场景六：手动查看全部当前事项

1. 用户点击“完整当前概览”，页面加载所有未解决事务、近期异常和关注事项。
2. 无新邮件时概览明确显示“本次无新增变化”；仍未完成的事项按优先级显示。
3. 该操作不推进来源游标、不生成新版本、不重复创建事务或提醒。

## 9. 功能优先级与落地顺序

### P0：保证信息正确和可行动

必须先完成，作为新简报体验的最小可用版本：

1. 概览、卡片、详情三级信息层级，消除正文与卡片重复。
2. 四类信息分类与三档优先级分离，卡片显示优先级原因。
3. 信息状态、处理状态、业务状态三套状态在 UI 和文案中分离。
4. 自动处理结果、失败原因、结果待核对和重试入口。
5. 手动增量模式与完整当前概览模式的明确切换。
6. 基于事项的跨简报去重、变化类型和延迟来源补齐。
7. 作业、提交/评分、截止变化与事务/日程的真实状态联动。

### P1：提高关注质量和用户控制

在 P0 稳定后加入：

1. 关注频率、来源偏好、免打扰时段和授权设置。
2. 持续关注、失败动作和临近截止的频率控制。
3. 低置信判断的确认流和可能重复事项提示。
4. 事务/日程/账单关联的统一操作收据和冲突提示。
5. 规则文稿与偏好设置的解释性预览，例如“此设置会隐藏哪些低价值动态”。

### P2：拓展信息中心能力

作为验证核心体验后的增强项：

1. 会前简报、周度变化回顾和跨来源主题视图。
2. 用户反馈驱动的优先级个性化建议。
3. 更多来源的事项归并和可验证字段抽取。
4. 面向多渠道的简报摘要投递，但所有渠道仍链接到同一桌面详情和业务对象。

不应在 P0 之前加入复杂标签体系、自由拖拽看板或独立的简报任务编辑器，这些会模糊简报与事务模块的职责。

## 10. 验收标准与衡量指标

### 10.1 产品验收

- 用户在首屏 10 秒内能说出本次发生的主要变化、Stella 已完成的动作和自己的下一步。
- 同一事项连续无变化时不重复出现；截止、状态、异常和延迟数据补齐能重新出现。
- 每个“已执行”状态都能打开目标业务对象并看到实际成功结果；失败不会被文案掩盖。
- 查看、忽略、确认、重试不会错误修改事务或日程的真实状态。
- 手动完整概览不会推进同步边界或重复执行联动。
- 作业“已提交”“已评分”“事务完成”三种事实可以同时、准确地展示。

### 10.2 建议指标

- 首屏到首次有效操作的时间。
- 需要行动卡片的打开率、完成率和逾期率。
- 连续简报重复事项率、用户主动隐藏率和误分类反馈率。
- 自动操作成功率、失败重试成功率、结果待核对比例。
- 每个来源的延迟数据补齐率和遗漏投诉率。
- 用户关闭/降低“其他动态”后的信息满意度变化。

## 11. 设计原则总结

Stella 简报应是一层可信的“变化和行动视图”：来源负责提供事实，Agent 负责理解和建议，事务/日程/账单负责维护业务状态，自动化负责按计划触发和重试。界面只把三者的关系讲清楚，并让用户用最少步骤完成下一步。这样可以在复用现有来源窗口、版本快照、投影 outbox 和桌面页面的基础上，逐步把简报从摘要页面变成可靠、连续、可控的信息中心。
