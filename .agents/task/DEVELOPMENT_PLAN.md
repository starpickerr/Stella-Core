
# Stella Development Plan

> **文档用途**：Stella 已确认开发需求的统一计划、阶段验收与开发进度记录。
> **需求基线**：Stella Codex 综合开发任务 **v2.1**，以及用户随后明确同意的六项开发效率要求。
> **规范优先级**：项目既有 `AGENTS.md`、适用的 Skill 与项目开发规范约束执行过程；本文定义本轮**做什么、依赖什么、如何验收、做到哪里**，不另立一套开发规范。
> **实际状态**：本文是计划，不代表功能已经完成；开始实施时必须核对本地工作区、既有成果与未提交修改。

### 1.2 不可突破的产品约束

1. **事务 UI 只重新设计顶部快捷聊天区域**。其下「全部事务 / 即将到期 / 未完成 / 已完成」导航、搜索筛选排序、事务树、子事务层级/进度、聚焦模式、面包屑、详情、原有操作及视觉布局保持原样。为通知功能补齐既有编辑控件时，仅做必要的局部适配，不借机重构事务主体。
2. **备用通知渠道可选且默认关闭**；未配置也能正常创建和运行任务；用户说「只通过飞书」时不得擅自改发微信或增加备用投递。
3. **Apple Calendar 和 Apple Reminders 共享合理的 EventKit 原生基础设施，但各自独立授权、业务模型、同步映射与冲突逻辑**。同步属于数据一致性能力，不自动等同于 Stella 的微信/飞书主动通知。
4. **Agent 与传统 UI 共享 Application API 和底层业务服务**；Agent 不得通过生成文本假装完成写入，也不得因工具缺失通过额外创建重复调度任务规避配置问题。
5. 保留所有用户数据、历史配置与未提交工作；涉及真实 Apple/外部渠道测试，必须遵循已有规范、必要授权和隔离测试目标。

## 2. 开发效率约束

以下规则只优化本轮任务的组织方式，不替代 `AGENTS.md` 或现有 Skill。

1. **任务去重与依赖分析**：实施前对照现有实现建立一次任务—模块映射，识别共享基础设施和前置依赖。属于同一业务域的需求统一设计接口，防止 Apple、通知、工具层和 UI 各自重复开发。同一能力只保留一个权威实现。
2. **分阶段开发、分阶段验收**：按下文阶段推进，每阶段只实施本阶段范围，满足验收条件后记录结果，再进入下一阶段；前置依赖未满足时不直接开发依赖模块。可独立的局部 Bug 可优先完成。
3. **减少重复读取项目代码**：优先依据路径、符号和调用关系定位，只读取当前阶段必要的代码范围。已有可信的分析结论先核对相关差异，不因切换任务无目的地重新扫描全项目。
4. **保存开发进度与决策**：完成每个阶段或确定关键接口后，更新本文「开发进度」和「架构决策」；记录实际修改、验证结果和剩余障碍。文档记录须与代码/Git 实情核对，不凭计划认定已完成。
5. **复用既有开发规范**：分支、测试、审查、Skill 和数据安全直接遵守项目现有 `AGENTS.md` 及相关规则；本文不重复定义工具链和通用流程。
6. **限制无关代码检查与重构**：修复局部 Bug 时优先最小变更；测试和检查依据项目规范覆盖受影响范围，避免无关的全面扫描、重复审查和顺手重构。必要的跨模块、安全和兼容性验证不能因为节省资源而跳过。

## 3. 依赖关系与实施分组

```text
阶段 0：核对工作区、恢复 Apple 中断上下文、去重与依赖映射
  ├─→ 阶段 1：两个独立的定时任务 P0 Bug（卡片点击 / 微信通道发现）
  ├─→ 阶段 2：统一通知配置、Agent/传统 UI、可靠投递、可选备用渠道
  │       └─依赖阶段 1 的通道发现结果；同一通知服务只实现一次
  └─→ 阶段 3：Apple EventKit → Calendar / Reminders 同步 → Agent 工具
          └─→ 阶段 4：统一 Apple 设置 + 日程/事务内嵌 Agent UI
                    （同时复用阶段 2 的渠道与通知能力）
阶段 5：Work 会话、项目和自动化工作区（与既有 Agent/调度保持兼容）
  └─→ 阶段 6：安全权限与 Custom（验证 Work、Shell、后台任务等统一边界）
```

**协调规则**：通知相关的「微信接入」「事务提醒渠道」「定时任务渠道」「失败恢复」「可选备用渠道」作为**一套通知领域能力**共同确定接口；Apple 相关的「原生接入」「双向同步」「Agent 工具」「设置中心」「业务入口」以**最终统一设计**推进，不先造临时独立设置页面再重做。不要为 Agent、人工 UI、后台服务创建彼此独立的同步或投递实现。

阶段 1、2 与 Apple 模块的部分工作可视依赖独立推进，但不得导致跨模块接口各自为政。每一阶段的实施细节以实际代码和已有开发规范为准。

## 4. 分阶段任务与验收

### 阶段 0｜现状核对与需求去重

**目标**：在改代码之前明确已完成、待完成、需调整的内容，尤其恢复上次中断的 Apple EventKit 工作。

**行动范围**：

- 检查实际工作区分支、未提交修改、现有测试和上次开发成果；优先保留并继续原有实现。
- 精确定位 Apple Calendar/EventKit、Reminders、日程/事务 UI、`TodoService`、`SchedulerService`、通知投递层、Agent 工具、Work 与安全系统。
- 按模块标注：`已存在且可复用 / 部分完成 / 待实现 / 与最终设计冲突`；记下最小改动边界及关键依赖。
- 不因重新规划覆盖本地数据或强行从零实现。**不预先新建重复的业务服务或文档**。

**验收**：形成精简的现状与依赖记录；可清楚识别 Apple 中断位置、阶段 1 的两个 Bug 入口及阶段 2/3 共用接口；不将未经验证事项标为已完成。

### 阶段 1｜定时任务两个明确 P0 Bug

#### 1A. 卡片点击错误跳转

**已知线索**：旧版 `desktop/src/renderer/src/pages/TasksPage.tsx` 依据 `linked_todo_id` 选择跳转 `/todos` 或打开任务编辑/详情。应先检查本地代码是否仍如此。

**要求**：

- 点击**整个定时任务卡片主体**，不论是否有 `linked_todo_id`，均打开**定时任务自身详情**。
- 点击独立的「关联事务」入口时，才前往对应事务详情；正确阻止事件冒泡，兼顾键盘操作。
- 任务详情保留调度计划、启停、执行状态、下次运行及关联信息；事务托管的字段继续遵循已有只读/业务约束。
- 关联事务不存在或不可读取时，仍能查看任务详情，并显示关联不可用提示。
- 原有启停、执行、编辑及其他按钮行为不变；不重设计任务页面或事务主体。

**验收**：普通和关联事务的任务点击均打开任务详情；明确点击关联事务才跳转事务；失效关联不阻塞详情；内部控件无误触。

#### 1B. 微信已接入但定时任务无法选择

**排查线索**：`ChannelManager`、`channel/channel_factory.py`、`agent/scheduler/delivery.py`、`agent/scheduler/integration.py`、`channel/weixin/weixin_channel.py`、`TasksPage.tsx`、`/api/scheduler/destinations`。旧实现可能因 `from app import ...` 与 `__main__` 的模块实例不一致获取不到实际通道；**须本地复现确认**。

**要求**：

- 通道管理 UI 与调度系统引用一致的运行时通道实例；已连接 `weixin` 正常显示在任务渠道列表。
- 已配置但临时不可用的通道可见且状态明确，不因单一 `ready=false` 直接消失。
- 区分未配置、未登录、没有可用接收人、具有接收人上下文、已知会话失效、未知状态；连接变化后可刷新。
- 接收人优先来自已建立的有效会话；保留既有 `context_token` 机制，不向前端泄露令牌。
- 不破坏 Desktop、飞书及其他通道现有行为。

**验收**：微信已接入时可选；无接收人/失效可解释；能在协议允许、用户授权的测试会话中进行真实发送验证，无法执行时标记未验证。

### 阶段 2｜统一通知配置、Agent 工具与可靠投递

**目标**：一次性解决「UI 能选渠道但 Agent 不能」「事务提醒和定时任务重复投递」「微信失效处理不足」等重叠问题。

#### 2A. 一套通知配置及投递能力

- 保留事务提醒属于 **TodoService**、独立定时任务属于 **SchedulerService** 的业务边界，复用统一通知投递基础设施。
- 支持结构化配置：首选 `channel_type`、已授权接收人、可选备用渠道及其接收人、启用状态、失败处理策略；最终字段遵循项目已有模型，不强制采用全新 Schema。
- 未明确指定渠道时保持兼容的默认行为；明确指定渠道时必须执行指定选择，不能偷换到其他默认通道。
- 修改事务提醒时间、渠道、完成/取消/删除事务时，关联调度按原业务生命周期正确更新，不得创建重复任务。
- 时间处理使用准确的时区转换，例如 `14:00+08:00` 等价 `06:00+00:00`；判断依据是**当地实际触发时间**而非数据库是否存储 UTC。

#### 2B. Agent / UI 能力一致

- 检查并扩展 `Todos Tool`、`Scheduler Tool` 及对应 Application API，使 Agent 能实际创建、查询、修改事务提醒和定时任务的渠道、接收人、备用配置和投递状态。
- 提供已连接渠道、主动投递能力、已授权接收人的查询/解析接口；接收目标不明确时询问用户，不能编造 ID，也不能假装已完成。
- 传统定时任务 UI 具有相应的首选渠道、接收人、测试发送、状态、备用配置；事务现有提醒编辑仅做必要的局部字段补齐，不重设计事务管理主体。
- 请求「只通过飞书」表示**仅首选飞书且不启用备用**；没有授权或发送条件时清楚报告。

#### 2C. 通知投递可靠性

- **任务执行结果与通知投递分别保存状态**：完成的简报或 Agent 结果不因发送失败而重新生成。
- 至少区分待发送、发送中、平台已接受、明确失败、等待恢复、结果未知、已过期；平台接受不等于用户最终送达。
- 微信 iLink 主动发送依赖可用会话和 `context_token`，存在不确定时效；创建时提示风险、可测试当前发送，但不保证未来有效；执行时再次检查并以 API 实际响应为准。
- 对明确失效停止无效重试，保存结果，等待用户重新建立会话；对临时故障有限重试；对结果未知避免盲目重复发送；补发考虑消息有效期，避免过期提醒堆积。
- 备用渠道**默认关闭**，启用与接收人均由用户明确选择，失败后只按用户授权的策略切换。没有备用渠道时仍可创建、运行和保留失败记录。
- 通道是否适合定时主动发送以已有实现及平台实际权限为准。优先保证当前 Desktop / 飞书 / 微信；其他已接入聊天通道不自动视为可主动推送，也不在本轮无依据地扩建。
- Stella 后端停止或 Mac 休眠/关机造成的漏执行需被正确表达，并遵循现有调度恢复机制；不将改用其他渠道误当成解决方案。

**验收场景**（Agent 应真实调用工具、持久化，UI 读取得到相同配置）：

- 「明天下午两点提醒我交作业，只通过飞书。」
- 「把这个事务的提醒从微信改成飞书。」
- 「每天早上八点通过微信发送邮件简报。」
- 「给这个定时任务增加飞书作为备用渠道。」
- 「关闭这个任务的备用渠道。」
- 「查询这个事务的提醒渠道和接收人。」
- 「把刚才的定时任务改成只发微信。」

**阶段验收**：UI / Agent 同一规则、通知不串渠、不重复建提醒、备用完全可选；发送失败不重新运行已完成 Agent；准确记录接收平台响应及未知状态。

### 阶段 3｜统一 Apple EventKit 与双向同步

**目标**：恢复已有 Calendar 成果后，以**一套原生基础设施 + 两套业务同步适配**完成 Apple 集成。

#### 3A. EventKit 基础设施

- 继续既有 Apple Calendar 原生实现，核对 Python/Electron 与 Swift（如使用）的通信、macOS 权限与打包运行，不做无依据推倒重写。
- 共享平台识别、EventKit 通信、连接状态、变化监听、同步调度、异常与诊断；Calendar、Reminders 分别维护系统授权。
- 非 macOS 平台正常降级；不绕过系统授权访问 Apple 数据。

#### 3B. Apple Calendar ↔ Stella Calendar

- 枚举系统可用日历（包含 iCloud、本地及系统已配置来源）；支持日历选择、读取/创建/更新/删除、全天、时区、重复规则及例外。
- 支持一次性导入/写入、单向/双向同步、手动/后台自动同步、数据变化监听、重试和重启恢复。
- 事件映射稳定、幂等、去重、防循环、冲突可检测；标识变化可恢复；外部来源暂时不可访问不能触发批量误删除。
- 首次同步、批量覆盖和删除采用安全保护；经现有 CalendarService / Application API 写入并与查询、简报、Agent 兼容。

#### 3C. Apple Reminders ↔ Stella Todos

- 基于 `EKReminder` 支持列表选择、读取/创建/更新/删除、完成/取消完成、手动/自动、单向/双向同步、变更监听与恢复。
- 正确转换可兼容的标题、备注、截止日期/时间、计划日期、提醒时间、优先级、完成状态/时间、重复规则和列表归属。
- **保留 Stella 多级事务、`parent_id`、子事务、依赖关系、进行中/等待/阻塞/取消等高级状态、聚焦模式及进度**；Apple 未完成不能覆盖非完成类状态，`cancelled` 不等于 `completed`；不因外部不支持字段而丢数据。
- 独立维护同步映射、冲突、幂等、循环和删除保护；权限撤销/列表不可访问时保留用户数据。经 TodoService / Application API 写入，保留简报及提醒调度兼容。

#### 3D. Apple Agent 工具

- 复用 Calendar/Todo 工具或增加清晰边界的 Apple 工具，允许查询授权、日历/列表、事件/提醒事项、同步状态、导入/写入及冲突处理。
- Agent 负责理解请求与授权交互；Sync Service 负责**确定性**同步；EventKit Adapter 负责系统访问；后台同步不依赖 LLM，不能为 UI/Agent/后台分别复制同步逻辑。

**验收**：在获得授权的隔离测试日历及提醒事项列表中，验证授权独立、双向同步、幂等、冲突、删除安全、重启恢复与高级事务字段不丢失。未执行的真机/打包测试如实标记。

### 阶段 4｜统一 Apple 设置与业务页面内嵌 Agent

**前置**：复用阶段 3 的同步与工具接口、阶段 2 的通知能力；先确定统一入口，不为旧交互建立临时设置页面。

#### 4A. Apple 互联设置中心

- 在现有设置体系建立 `设置 → 集成与连接 → Apple`，集中展示独立的 **Apple 日历**、**Apple 提醒事项**配置。
- 各自支持：授权状态、已选日历/列表、同步方向、自动开关、最近同步时间、手动同步、一次性导入与写入、错误/冲突记录、断开连接。
- 人工操作遵循「选来源/目标 → 选范围 → 预览新增/更新/跳过/冲突 → 确认执行」。**一次性导入不自动开启持续同步**。
- 传统 UI、Agent、后台同步使用同一 Sync Service 和配置源；两业务页面的「管理 Apple …」入口直接打开相应设置。

### 阶段 5｜Work 工作区隔离与兼容

目标结构（位于既有用户级 `work/` 内，遵循实际用户/Agent 身份机制）：

```text
work/
├── sessions/<agent_id>/<session_id>/
├── shared/
└── automations/<agent_id>/<task_id>/
```

- **普通聊天**：独立会话工作目录、会话恢复沿用、按需创建；不同聊天默认不互访私有文件。
- **项目聊天**：使用项目实际目录，同项目会话共享项目文件；项目绑定失效时明确处理，不偷偷回退到他处。
- **自动化任务**：保留既有 `scheduler/`、`runs/` 等业务数据存储；独立任务以 `task_id` 保持稳定工作目录，多次运行复用；项目任务用已授权项目目录；无文件操作不必创建目录。保留 `source/reuse/new` 对话模式，但引用会话不等于获得该会话私有文件权限。
- **受控共享**：`work/shared/` 中显式选择文件，支持只读/可修改和撤销，不因共享单文件开放整个目录。
- **统一解析**：Agent Runtime、文件工具、Shell、后台进程、文件搜索/预览、自动化、SecurityGateway、ProcessSandbox 使用一致工作区上下文；仅更改 `cwd` 不构成安全隔离。
- **兼容迁移**：旧 `work/` 文件与历史会话可安全访问/迁移，提供合理保留和清理行为，不误删其他会话/项目/任务/共享文件。Apple 同步和投递记录为业务数据，不存放普通聊天私有工作区。

**验收**：会话/项目/任务归属正确、权限边界一致、历史文件保留、共享与撤销有效、自动化重复运行沿用稳定目录。

### 阶段 6｜安全权限与 Custom

- 实现或完善四种模式：**Read Only、Workspace Write、Full Access、Custom**。
  - Read Only：授权范围内读取，禁止未经授权写入。
  - Workspace Write：允许当前工作区自主创建/修改/删除，工作区外操作另行授权。
  - Full Access：放宽一般文件/Shell/网络规则，但**不绕过**操作系统、用户身份、跨聊天私有资源、受管理资源、Apple 系统授权及其他外部业务权限。
  - Custom：细粒度文件/目录读写、额外路径、Shell、网络、`Allow/Confirm/Deny`、MCP、Browser、Git/GitHub、Skill 及内部受管理资源；可复制预设、保存、恢复默认及查看有效规则。
- 区分 **Sandbox（执行环境隔离）**、**Approval（授权/审批）**、**Tool Permissions（工具操作规则）**，复用现有 SecurityGateway、SecurityPolicy、ProcessSandbox 和审批机制。
- 防范跨工作区访问、路径穿越、符号链接逃逸、Shell/脚本/子进程、后台进程及 Browser/MCP 间接越权、错误审批复用和工作区切换后的权限错用。
- 安全中心按现有 UI 增强四模式、Custom、工作区/有效权限、沙箱状态、审批与必要风险说明；不删除既有凭据、连接、审计等功能。
- 保守兼容历史 `approval`、`project-full`、`full-access`、`custom` 配置，不能意外提升授权或遗失用户设置；无法实际执行的沙箱限制应如实说明，不能仅用 UI/提示词声称安全。
- 用户授权的备用通知渠道和 Apple 授权与普通文件权限独立。

**验收**：四模式及 Custom 规则实际生效，Work/工具/Shell/后台任务边界一致；旧配置迁移安全；真实隔离能力已验证或明确标注未验证。

## 5. 跨阶段统一验收

- **业务真实性**：Agent/传统 UI 操作均经过实际 Application API；不以自然语言承诺替代成功写入；后台同步和通知投递不以 LLM 逐项处理。
- **数据安全**：不重复造提醒、不因 Apple 同步丢失事务属性、不因通知失败重复执行已完成任务、不误删用户数据；老数据及配置安全兼容。
- **渠道安全**：已连接微信可见；首选渠道/接收人按用户指定，备用默认关闭；不可投递时记录实际原因；平台接受不等于最终送达。
- **UI 边界**：定时任务卡片点击与关联事务入口分离；事务页面下部保持原状；Apple 设置为唯一管理中心。
- **时间正确性**：验证用户所在地的实际提醒/调度时间、时区及重复任务，而非根据 UTC 存储字符串误判。
- **验证记录**：按照既有规范运行受影响范围的必要验证；每项记录 `PASS / FAIL / SKIP（原因）`。需要真实 macOS EventKit 或外部渠道授权的测试，使用测试数据与测试接收目标；没有实际运行就不能写通过。
