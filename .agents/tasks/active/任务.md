# 任务

任务分为「问题修复」和「功能新增」。问题修复保留已有需求；功能新增在现有安全中心设计基础上补充后台任务权限与数据隐私管理能力。

## 一、问题修复

### 1. 安全中心外部连接状态与实际服务状态不一致

#### 问题描述

Stella 安全中心的「外部连接」页面未能准确反映各服务的真实连接状态，导致安全中心、实际功能配置和总览统计之间存在不一致。

具体表现为：

1. **浏览器**：固定显示「已连接」，不反映实际运行状态或可用性。
2. **邮箱**：即使已在简报功能中配置邮箱，安全中心仍可能显示「未连接」。
3. **Apple 日历**：即使已获得 EventKit 授权并完成连接，安全中心仍可能显示「未连接」。
4. **GitHub**：仅根据 Token 是否存在判断连接状态，没有验证凭据是否有效。
5. **Plugins 和 External API**：连接状态固定为「未连接」，不反映实际启用情况。
6. **总览统计**：连接数量直接依据上述状态计算，可能与实际可用服务数量不符。
7. **权限范围**：当连接未声明具体操作范围时，页面错误地显示「全部操作」，容易误导用户对实际权限的理解。

#### 原因分析

**根本原因：安全中心缺少统一的连接状态查询机制，不同功能使用不同的数据来源和判断标准。**

通过代码核验，确认以下问题：

1. `agent/permission/center.py` 中的 `connections()` 维护了一份固定连接目录，通过硬编码、配置字段和环境变量判断连接状态，没有统一读取各服务的实际状态。
2. **邮箱状态来源不一致**：简报邮箱使用 `agent/briefing/settings.py` 管理邮箱账户、配置和 IMAP 连接检测，而安全中心仅检查通用的 `email_password` 或 `EMAIL_PASSWORD` 字段。
3. **Apple 日历状态来源不一致**：日历服务通过 `agent/calendar/apple_sync.py` 获取 EventKit 授权状态及实际连接状态，而安全中心仅检查 `calendar_token` 或 `CALENDAR_TOKEN`。
4. **浏览器状态被硬编码**：`agent/tools/browser/browser_tool.py` 已具备运行状态检测能力，但安全中心直接将 `connected` 设置为 `True`。
5. **状态判断标准不统一**：GitHub 仅判断凭据是否存在，MCP 则通过 `ToolManager.list_mcp_status()` 获取部分真实运行状态。不同服务对「已连接」的定义不一致。
6. **错误状态被直接用于统计**：`overview()` 根据 `connections()` 返回的 `connected` 和 `allowed` 计算连接数量，没有进一步验证服务的实际可用性。
7. **连接状态与权限状态混淆**：系统没有清晰区分「已配置」「已授权」「可用」「允许 Agent 使用」等不同状态。此外，安全中心连接列表主要读取全局连接策略，可能无法准确反映项目或会话级的有效权限。

目前未发现错误的连接状态直接导致权限绕过的证据，主要问题集中在状态管理、信息展示和统计准确性。

#### 修复方向

**建立统一的连接状态查询机制，让安全中心成为各服务真实状态的聚合展示入口，而不是独立维护另一套连接判断逻辑。**

1. **统一连接状态接口**

   - 为各类外部服务建立统一的状态查询契约。
   - 区分已配置、已授权、可用、连接异常及已撤销等状态。
   - 独立记录服务授权范围和 Stella 的执行权限，避免混淆。
   - 优先复用已有服务接口，不重复实现连接管理逻辑。
2. **接入真实服务状态**

   - 邮箱：读取简报邮箱配置，区分账户是否启用、配置是否完整以及连接检测结果。
   - Apple 日历：读取 EventKit 授权状态、实际连接状态及同步配置。
   - 浏览器：区分浏览器能力是否可用、工具是否允许调用以及浏览器实例是否运行。
   - GitHub：区分 Token 已配置和凭据已验证。
   - MCP：保留现有运行状态检查机制，并纳入统一状态模型。
   - Plugins、External API：读取实际启用和可用状态，不再使用固定布尔值。
3. **统一安全中心与总览的数据来源**

   - 连接列表由真实服务实例和状态提供方生成。
   - 总览统计与连接列表使用相同的数据来源和判断规则。
   - 仅将已验证可用且当前权限允许使用的服务实例计入可用连接数量。
   - 服务断开、授权撤销、配置删除或凭据失效后，页面与统计能够正确更新。
4. **修正权限范围展示**

   - 空范围显示为「未声明范围」，而不是「全部操作」。
   - 分别展示服务自身的授权范围和 Stella 的执行权限。
   - 根据当前有效权限策略展示 Agent 是否允许使用该连接。
   - 保留现有 `SecurityGateway` 权限校验机制，避免因状态展示调整影响安全边界。
5. **补充自动化测试**

   - 验证未配置服务时的连接状态和总览数量。
   - 验证邮箱、Apple 日历配置完成后的状态同步。
   - 验证连接断开、授权撤销和凭据失效后的状态更新。
   - 验证多账户、多连接实例及 MCP 状态变化。
   - 验证全局、项目和会话级权限对连接展示的影响。
   - 确保展示状态变化不会绕过现有权限校验。

**验收标准：** 安全中心展示的连接状态、权限信息及总览统计与实际服务状态一致；连接管理仍由各服务负责，安全中心统一读取和展示，不再依赖硬编码状态或重复的连接判断逻辑。

### 2. 安全中心权限管理设计不合理，默认权限与项目、对话权限职责不清晰

#### 问题描述

Stella 安全中心目前将「默认权限」与「项目与对话」分为两个独立页面，权限配置分散，且「自定义」的含义及作用范围不够明确。

具体问题包括：

1. **权限管理入口分散**：默认权限、项目权限和对话权限分别配置，用户难以在同一页面查看和管理所有权限。
2. **默认权限定位不清晰**：默认权限应作为新建项目和新建对话时的初始权限，而不是持续影响已有项目和对话的继承规则。
3. **自定义权限概念模糊**：默认权限提供「自定义」选项，但项目和对话也可以自定义，容易混淆不同层级的作用范围。
4. **权限独立性不足**：每个项目和对话应能够独立选择权限方案，不同项目、不同对话的自定义规则应互不影响。
5. **权限修改存在意外副作用**：点击全局「自定义」时，系统会在用户尚未保存的情况下提前提交权限配置。
6. **权限编辑逻辑不合理**：当前项目和对话的规则编辑器允许在基础预设下逐项修改权限，并提供「沿用上级设置」选项，导致基础预设与自定义规则的边界不清晰。
7. **权限展示不够直观**：用户难以快速了解每个项目和对话当前使用的权限方案，以及具体的自定义规则。

#### 原因分析

**根本原因：当前权限管理系统混合了全局默认配置、项目权限、对话权限以及自定义规则，缺少明确的初始化机制和独立管理模型。**

通过现有代码分析，确认以下问题：

1. `SecurityPage.tsx` 将默认权限与项目、对话权限分开管理，没有形成统一的权限管理界面。
2. `security_policy.py` 通过 `resolve()` 按全局、项目、对话的顺序合并权限配置。当前机制以动态继承和规则覆盖为主，不符合「创建时采用默认权限，创建后独立管理」的目标设计。
3. 当前权限预设包含 `read-only`、`workspace-write`、`full-access`、`custom` 四种模式，将「自定义」与三个基础权限预设并列，同时又允许全局、项目和对话分别修改规则，造成概念混淆。
4. 项目和对话目前主要通过局部规则覆盖实现差异化配置，尚未形成明确的独立权限配置模型。
5. 当前 `PolicyEditor` 在基础方案下仍允许修改具体规则，并提供「沿用上级设置」选项，使权限方案与实际生效规则之间存在理解成本。
6. 前端在用户选择全局「自定义」时直接调用保存接口，导致编辑状态与持久化状态没有严格分离。
7. 默认权限页面使用当前上下文的 `effective_mode` 判断选中状态，可能受到项目和对话权限影响，无法准确反映全局默认配置。

#### 修复方向

**将安全中心的「默认权限」与「项目与对话」合并为统一的「权限管理」页面，保留现有 UI 的卡片布局、选择器及规则编辑样式，采用「默认权限初始化 + 项目与对话独立配置」的设计。**

##### 1. 合并权限管理页面

将现有「默认权限」和「项目与对话」两个页面合并为「权限管理」。

页面自上而下分为三个区域：

- **默认权限**：设置新建项目和新建对话的初始权限。
- **项目权限**：查看和修改每个项目的独立权限。
- **对话权限**：查看和修改每个对话的独立权限。

保留现有页面的视觉风格、卡片布局、下拉选择器和规则列表，不进行无关 UI 重构。

##### 2. 重新定义默认权限

页面顶部保留现有的权限预设卡片设计，但仅展示三种权限：

| 权限方案                      | 说明                                             |
| ----------------------------- | ------------------------------------------------ |
| 只读（Read Only）             | 在授权范围内读取，未授权的写入会被拒绝           |
| 工作区写入（Workspace Write） | 允许在授权工作区内自主修改，工作区外操作需要授权 |
| 完全访问（Full Access）       | 放宽一般文件与命令限制，仍保留系统强制安全边界   |

**移除默认权限区域中的「自定义」卡片。**

默认权限的作用仅限于新建项目和新建对话时的权限初始化：

- 新建项目时，自动采用当前默认权限。
- 新建对话时，自动采用当前默认权限。
- 创建后将权限保存为该项目或对话的独立配置。
- 修改默认权限只影响之后新建的项目和对话。
- 已存在的项目和对话不受默认权限修改影响。

例如：

```text
初始默认权限：工作区写入
│
├── 项目 A：工作区写入
└── 对话 A：工作区写入

修改默认权限：只读
│
├── 项目 A：工作区写入（保持不变）
├── 对话 A：工作区写入（保持不变）
├── 新建项目 B：只读
└── 新建对话 B：只读
```

默认权限区域只显示全局默认配置，不使用当前项目或对话的有效权限判断选中状态。

##### 3. 项目与对话支持四种独立权限方案

保留现有「项目与对话」区域的 UI 设计，包括项目选择器、权限调整入口和规则编辑器。

每个项目和对话只能选择以下四种权限：

| 权限方案   | 项目 | 对话 |
| ---------- | ---- | ---- |
| 只读       | ✅   | ✅   |
| 工作区写入 | ✅   | ✅   |
| 完全访问   | ✅   | ✅   |
| 自定义     | ✅   | ✅   |

**项目和对话的权限选择器只允许上述四种选项，不提供「沿用默认权限」或「沿用上级设置」作为权限方案。**

具体交互规则：

- 选择「只读」：直接采用完整的只读预设，不允许逐项修改权限。
- 选择「工作区写入」：直接采用完整的工作区写入预设，不允许逐项修改权限。
- 选择「完全访问」：直接采用完整的完全访问预设，不允许逐项修改权限。
- 选择「自定义」：展开详细权限编辑器，允许逐项调整权限。

选择前三种预设时，具体权限规则由系统预设决定。可以保留只读的规则说明，但不显示可编辑控件。

**只有选择「自定义」时，才能修改具体权限规则。**

##### 4. 重新设计自定义权限编辑逻辑

保留当前规则编辑器的分组、排列方式、说明文字和下拉选择器样式。

选择「自定义」后，使用当前权限的有效规则初始化编辑草稿。

自定义规则中的每个权限项只能选择以下三种状态：

| 权限设置 | 含义                    |
| -------- | ----------------------- |
| 允许     | 允许 Agent 执行该类操作 |
| 禁止     | 拒绝 Agent 执行该类操作 |
| 先询问我 | 执行前需要获得用户确认  |

**移除规则选择器中的「沿用上级设置」选项。**

自定义权限示例：

```text
权限方案：自定义

文件与项目
├── 查看项目文件        允许
├── 修改项目文件        禁止
└── 访问项目外的文件    先询问我

系统操作
├── 运行终端命令        允许
├── 使用版本管理        允许
├── 访问网络            允许
├── 安装软件依赖        先询问我
└── 启动后台任务        禁止

服务与敏感操作
├── 使用外部服务        允许
└── 执行高风险操作      先询问我

[取消]                   [保存]
```

具体要求：

1. 自定义规则必须明确保存每个权限项的设置，不依赖动态继承。
2. 每个项目和对话拥有独立的自定义权限配置。
3. 不同项目可以使用不同的自定义规则。
4. 不同对话可以使用不同的自定义规则，即使它们属于同一个项目。
5. 修改一个项目或对话的自定义规则，不影响其他项目、对话或全局默认权限。
6. 从基础预设切换至自定义时，自动填充当前预设的权限规则作为初始草稿。
7. 再次进入已有自定义配置时，加载此前保存的具体规则，不重置为默认值。
8. 切换回基础预设时，实际生效规则必须严格与所选预设一致。

##### 5. 修复权限提前保存问题

所有项目和对话的权限编辑都应严格区分草稿状态与已保存状态。

- 选择权限方案时，先更新界面草稿。
- 选择「自定义」时，只展开规则编辑器，不立即修改实际权限。
- 修改规则时，仅更新本地草稿。
- 点击「保存」后，统一提交权限方案和具体规则。
- 点击「取消」时，恢复上次已保存的配置。
- 退出页面或刷新时，不保存未提交的修改。
- 保存失败时保留草稿，并显示错误原因。

对于顶部的全局默认权限，也应保证用户操作与持久化结果一致，避免出现未确认的配置变更。

##### 6. 优化权限展示

保留项目选择器和现有权限调整区域，减少页面结构变化。

项目与对话列表直接展示当前权限方案：

| 名称         | 当前权限   | 操作     |
| ------------ | ---------- | -------- |
| Stella 项目  | 自定义     | 调整权限 |
| 数学建模项目 | 工作区写入 | 调整权限 |
| 课程作业项目 | 只读       | 调整权限 |
| 对话 A       | 完全访问   | 调整权限 |
| 对话 B       | 自定义     | 调整权限 |

展示规则：

- 基础预设直接显示对应权限名称。
- 自定义配置统一显示「自定义」。
- 展开自定义配置后，显示该项目或对话实际保存的完整权限规则。
- 规则编辑器仅在自定义模式下可编辑。
- 页面显示的权限方案必须与后端实际执行权限一致。

##### 7. 调整权限配置与持久化机制

根据新的权限模型调整前后端数据结构和权限解析逻辑。

核心要求：

1. 全局默认权限仅保存三种基础预设之一。
2. 项目和对话分别保存独立的权限方案。
3. 自定义权限保存完整规则，不依赖全局或上级配置的后续变化。
4. 已存在项目和对话的权限不会因默认权限调整而变化。
5. 不同项目、不同对话的权限配置必须相互隔离。
6. 保留已有 `SecurityGateway` 权限校验机制及系统强制安全边界。
7. 明确项目与所属对话之间的权限约束关系，防止出现界面配置与实际执行权限不一致的问题。
8. 兼容历史权限配置，迁移时保留原有实际权限，不得意外扩大或收紧权限。

##### 8. 补充自动化测试

至少覆盖以下场景：

1. 新建项目自动采用当前默认权限。
2. 新建对话自动采用当前默认权限。
3. 修改默认权限不影响已有项目和对话。
4. 项目和对话权限选择器仅提供四种方案。
5. 选择前三种预设时不能逐项修改权限。
6. 只有选择「自定义」时才能编辑具体规则。
7. 自定义规则选择器仅提供「允许」「禁止」「先询问我」三种选项。
8. 不同项目的自定义规则互不影响。
9. 不同对话的自定义规则互不影响。
10. 自定义配置在保存、刷新和重新进入后保持一致。
11. 未保存的权限修改不会影响实际执行。
12. 从自定义切换至基础预设后，实际执行权限与所选预设一致。
13. 历史权限配置能够正确迁移，且不发生意外权限变化。
14. 前端展示、后端持久化和 `SecurityGateway` 的实际权限判断保持一致。

#### 验收标准

安全中心通过统一的「权限管理」页面管理全局默认权限、项目权限和对话权限，并保留现有 UI 风格及主要交互结构。

**最终权限设计必须满足：**

- **默认权限**：只有「只读」「工作区写入」「完全访问」三种，用于新建项目和新建对话时的权限初始化。
- **项目权限**：只有「只读」「工作区写入」「完全访问」「自定义」四种，每个项目独立保存。
- **对话权限**：只有「只读」「工作区写入」「完全访问」「自定义」四种，每个对话独立保存。
- **自定义权限**：只有「允许」「禁止」「先询问我」三种具体规则设置，不提供「沿用上级设置」。
- **编辑行为**：只有自定义模式允许修改具体规则，且所有修改必须明确保存后才生效。
- **权限独立性**：修改默认权限、其他项目或其他对话的权限，不会意外改变已有独立配置。
- **安全一致性**：权限界面、持久化配置与实际工具执行结果一致，且不能突破系统强制安全边界。

### 3. 定时任务未明确展示实际执行权限及来源

#### 问题描述

Stella 定时任务卡片目前仅显示「沿用绑定对话」，没有明确展示任务实际使用的权限方案及权限来源。

具体问题包括：

1. **权限信息不透明**：用户无法直接判断定时任务使用「只读」「工作区写入」「完全访问」还是「自定义」权限。
2. **权限来源不明确**：任务可能使用绑定对话的权限，也可能使用独立指定的运行权限，但界面没有清晰区分。
3. **自定义权限不可见**：当绑定对话使用自定义权限时，任务卡片没有展示具体的权限规则。
4. **权限变化缺少反馈**：如果绑定对话的权限被修改，用户无法直观了解定时任务的实际执行权限是否随之变化。

#### 原因分析

**根本原因：定时任务已有权限解析机制，但前端没有完整展示最终有效权限及其来源。**

通过代码分析，确认以下问题：

1. `agent/scheduler/mutations.py` 支持 `run_permission_mode`，允许任务明确指定运行权限，未指定时则使用对应执行上下文的权限。
2. `agent/runtime/tool_invocation.py` 在任务执行时解析权限配置，包括关联对话、所属项目及任务自身的权限预设。
3. `desktop/src/renderer/src/pages/TasksPage.tsx` 主要根据任务保存的 `run_permission_mode` 展示权限标签，未查询最终有效权限。
4. 当前任务数据缺少面向 UI 的统一权限说明，无法直接展示权限方案、来源及具体规则。

#### 修复方向

1. 定时任务卡片明确展示实际执行权限，包括权限方案和权限来源。
2. 权限方案应与安全中心保持一致：

   - 只读
   - 工作区写入
   - 完全访问
   - 自定义
3. 明确区分权限来源：

   - 使用绑定对话权限。
   - 使用任务独立指定的权限。
4. 当任务使用绑定对话权限时，读取对应对话的有效权限配置，而不是仅显示「沿用绑定对话」。
5. 当任务使用自定义权限时，支持查看实际生效的完整权限规则，包括「允许」「禁止」「先询问我」。
6. 对话权限发生变化后，任务卡片应在刷新时展示最新的有效权限。
7. 对无法解析权限的任务，明确显示状态异常及原因，避免错误展示为默认权限。
8. 确保任务卡片展示的权限与实际执行时 `SecurityGateway` 使用的权限一致。

**验收标准：** 用户无需进入安全中心，即可在定时任务中明确查看任务实际采用的权限方案及来源；自定义权限可查看具体规则，界面展示与后端执行保持一致。

### 4. 修改定时任务发送渠道会清除执行对话绑定

#### 问题描述

Stella 定时任务的执行上下文与结果发送渠道存在不合理的耦合。

用户修改任务的发送渠道时，系统可能同时清除原有的执行对话绑定及项目相关配置，导致任务执行环境发生非预期变化。

例如：

原始任务配置：

| 配置项   | 内容                    |
| -------- | ----------------------- |
| 任务     | 每天生成邮件简报        |
| 执行对话 | 对话 A                  |
| 执行权限 | 使用对话 A 的自定义权限 |
| 发送渠道 | Stella 客户端           |

用户仅修改发送渠道：

`Stella 客户端 → Telegram`

预期结果：

- 执行对话仍为对话 A。
- 执行权限保持不变。
- 仅将执行结果发送至 Telegram。

但当前实现可能清除执行对话绑定，导致后续执行使用其他上下文和权限来源。

#### 原因分析

**根本原因：定时任务将执行对话信息与消息发送渠道保存在相互关联的数据结构中，渠道切换时错误地清除了执行配置。**

通过代码分析，确认以下问题：

1. `desktop/src/renderer/src/pages/TasksPage.tsx` 中的 `buildAction()` 根据发送渠道决定是否保留对话配置。
2. 当渠道不是 `web` 时，前端会删除以下字段：

   ```text
   conversation_mode
   source_session_id
   conversation_space
   execution_project_dir
   ```
3. `agent/scheduler/mutations.py` 中的 `_route_action()` 和 `update()` 也存在类似逻辑，切换到非 `web` 渠道时会再次清除这些字段。
4. `agent/scheduler/conversation.py` 的验证逻辑要求对话模式与 `web` 渠道关联，使执行对话无法独立于消息发送渠道存在。
5. 由于执行权限可能依赖绑定对话及其项目配置，清除对话绑定可能间接改变实际执行权限。

#### 修复方向

**将任务执行上下文与消息发送配置彻底解耦，保证修改发送渠道不会影响任务如何执行。**

1. 明确区分两类配置：

   **执行上下文**

   - 执行对话。
   - 对话模式。
   - 所属项目或工作区。
   - 执行权限来源。

   **结果发送**

   - 发送渠道。
   - 接收目标。
   - 发送相关参数。
2. 修改发送渠道时，只更新结果发送配置，不修改执行对话、项目或权限信息。
3. 移除前后端根据 `channel_type` 自动删除执行对话字段的逻辑。
4. 保留现有三种对话执行方式：

   - 使用已有对话。
   - 复用任务专用对话。
   - 每次执行创建新对话。
5. 三种对话模式均应独立于消息发送渠道，不因渠道变化而改变。
6. 调整任务数据模型及更新接口，确保执行配置和发送配置分别保存、分别更新。
7. 对已有定时任务进行兼容处理，保留原有有效的执行绑定信息。
8. 补充跨渠道修改测试，重点验证：

   - Stella 客户端切换 Telegram。
   - Telegram 切换 Stella 客户端。
   - 修改接收目标但不修改执行上下文。
   - 修改发送渠道后任务仍使用原有权限。
   - 保存、刷新及实际执行时配置保持一致。

**验收标准：** 用户修改定时任务的发送渠道或接收目标时，任务原有的执行对话、所属项目及执行权限保持不变；只有用户主动修改执行设置时，才允许改变这些配置。

### 5. 定时任务对话管理依赖历史 Web 渠道逻辑，与桌面客户端定位不一致

#### 问题描述

Stella 当前以桌面客户端（Desktop）为主要产品形态，但定时任务系统中仍保留了部分以 `web` 渠道为前提的对话管理逻辑。

需要注意，代码中的 `channel_type = "web"` 不一定代表仍在开发独立 Web 端，它也可能是桌面客户端沿用的内部会话渠道标识。

目前主要问题包括：

1. **内部概念混淆**：桌面客户端的任务执行逻辑仍依赖 `web` 渠道标识，容易混淆产品平台、执行上下文和消息发送渠道。
2. **执行能力受到渠道限制**：对话模式的配置和验证依赖 `channel_type = "web"`，非 Web 渠道无法使用同一套执行对话管理逻辑。
3. **执行与通知职责不清晰**：定时任务将部分执行上下文信息保存在渠道相关字段中，导致不同渠道之间的行为不一致。
4. **历史架构增加维护成本**：开发人员需要理解 `web` 在不同模块中的具体含义，容易在新增桌面功能或外部发送渠道时引入兼容性问题。

#### 原因分析

**根本原因：定时任务中的对话管理逻辑仍以历史渠道模型为基础，没有完全独立于桌面客户端和结果发送机制。**

通过代码分析，确认以下问题：

1. `agent/scheduler/conversation.py` 中的 `validate_conversation_action()` 将对话模式与 `channel_type = "web"` 绑定。
2. `agent/scheduler/conversation.py` 中的 `prepare_run()` 负责解析执行对话，包括已有对话、复用对话和新建对话三种模式。
3. `agent/scheduler/integration.py` 使用 `prepare_run()` 生成任务执行上下文，但部分后续行为仍依据消息渠道决定。
4. `desktop/src/renderer/src/pages/TasksPage.tsx` 仅在 `channel === 'web'` 时展示对话模式选择器。
5. 现有代码没有充分区分：

   - 桌面客户端作为产品运行平台。
   - Agent 执行任务所使用的对话上下文。
   - 任务结果发送使用的通信渠道。

需要进一步核验 `web` 标识在桌面消息、会话存储及渠道路由中的其他用途，不能直接将其全部替换为 `desktop`。

#### 修复方向

**保留 Stella 桌面客户端的现有能力，梳理并统一内部概念，使任务执行上下文不再依赖历史 Web 渠道标识。**

1. 明确区分三个核心概念：

   | 概念              | 职责                               |
   | ----------------- | ---------------------------------- |
   | Desktop           | Stella 桌面客户端运行平台          |
   | Execution Context | Agent 执行任务时使用的对话与工作区 |
   | Delivery Channel  | 任务结果的消息发送渠道             |
2. 将对话模式管理从发送渠道逻辑中独立出来，由定时任务的执行配置负责。
3. 三种对话模式均应支持桌面客户端创建的定时任务，不再以 `channel_type = "web"` 作为使用条件。
4. 梳理 `web` 在现有代码中的不同含义，区分历史命名与仍然有效的内部会话协议。
5. 对于仅作为内部协议标识使用的 `web`，优先通过接口适配和语义整理解决问题，不进行无必要的全局重命名。
6. 桌面客户端统一使用任务执行上下文接口，不依赖结果发送渠道决定对话绑定关系。
7. 保留 Telegram、飞书等外部消息发送能力，将其明确定位为结果发送渠道，而不是任务执行环境。
8. 清理已经失效的 Web 端专属分支和不再使用的兼容逻辑，但必须先确认调用关系及真实用途，避免影响桌面客户端现有功能。
9. 补充测试，确保：

   - 桌面客户端能够正常创建和编辑定时任务。
   - 三种对话模式均能正常执行。
   - 切换发送渠道不影响执行上下文。
   - 桌面会话和任务执行记录正确关联。
   - 现有外部消息渠道及历史任务数据保持兼容。
   - 不会因清理历史逻辑造成桌面客户端功能回归。

**验收标准：** Stella 定时任务系统能够清晰区分桌面客户端、任务执行上下文和消息发送渠道；三种对话模式独立于发送渠道工作，现有桌面功能及外部通知渠道保持兼容，不再因为历史 `web` 渠道判断而限制执行能力。

## 二、功能新增

### 1. 安全中心新增「后台任务权限」

#### 功能描述

Stella 支持定时任务及后台自动执行，但任务可能在用户不使用客户端时运行，因此需要提供独立、透明的权限管理能力。

安全中心新增「后台任务权限」页面，集中展示所有后台任务的权限配置、执行上下文和授权状态，让用户了解后台任务可以执行哪些操作、使用什么权限，以及需要授权时如何处理。

#### 设计要求

##### 1. 后台任务权限列表

展示所有已配置的后台任务。以下内容仅为展示示例，实际信息应读取任务数据和有效权限：

| 任务名称 | 执行权限 | 权限来源 | 状态 |
| -------- | -------- | -------- | ---- |
| 每日邮件简报 | 只读 | 独立设置 | 已启用 |
| GitHub 项目检查 | 自定义 | 对话 A | 已启用 |
| 文件整理 | 工作区写入 | 独立设置 | 已暂停 |

支持按任务名称、权限方案和启用状态筛选，并支持查看执行上下文和授权状态。

##### 2. 任务权限管理

每个任务应明确区分：

- **执行上下文**：使用已有对话、复用任务专用对话或每次创建新对话。
- **执行权限**：使用绑定对话的权限，或由用户独立指定运行权限。
- **发送渠道**：仅负责发送执行结果，不影响执行上下文和权限。

任务使用绑定对话权限时，应读取该对话的实际有效权限。

任务使用独立权限时，应明确保存其权限配置，包括所选权限方案及自定义模式下的完整规则，不依赖消息发送渠道。

对于没有绑定已有对话的任务，必须明确确定运行权限，避免使用来源不清晰的隐式权限。权限方案和规则状态与「问题修复」第 2、3 项保持一致。

##### 3. 无人值守授权机制

普通对话可以实时弹出授权窗口，但后台任务执行时，用户可能不在线。

| 权限设置 | 后台执行行为 |
| -------- | ------------ |
| 允许 | 在其他安全规则也允许的前提下正常执行 |
| 禁止 | 直接拒绝对应操作 |
| 先询问我 | 没有获得用户确认前，不得执行对应操作 |

对于无人值守任务，如果无法获得实时确认，应暂停或终止当前受限操作，记录原因，并通过已有通知机制告知用户。

不得因为任务自动执行就绕过权限校验，也不能将「先询问我」自动解释为允许。

##### 4. 任务权限变更

支持查看和调整任务执行权限，并满足：

1. 修改任务权限必须由用户明确确认。
2. 修改发送渠道不能改变任务权限。
3. 修改绑定对话时，重新解析对应权限。
4. 任务执行时使用的权限必须与界面展示一致。
5. 权限变更应记录在安全活动中。

##### 5. 与定时任务页面保持一致

安全中心负责集中查看和管理后台任务权限；定时任务页面继续负责任务内容、执行时间、通知渠道等业务设置。

两个页面使用同一份任务数据与权限配置，复用同一套权限解析和更新接口，避免重复维护。

本功能与「问题修复」第 3、4、5 项共同使用解耦后的任务执行上下文与结果发送配置，不重新实现定时任务管理。

#### 验收标准

用户能够在安全中心清楚查看每个后台任务的执行权限及来源，并能够在明确确认后调整权限。后台任务在无人值守状态下不会绕过需要确认的操作，修改通知渠道不会改变任务执行权限，权限变更可在安全活动中查看。

### 2. 安全中心新增「数据与隐私」

#### 功能描述

Stella 作为私人 AI 助手，可能处理对话记录、邮件、日历、项目文件、任务信息和外部服务数据。

安全中心新增「数据与隐私」页面，让用户了解 Stella 保存了哪些用户数据、数据存储在哪里、哪些数据可能发送给外部服务，以及如何管理或删除支持清理的数据。

#### 设计要求

##### 1. 本地数据管理

展示 Stella 实际保存的用户数据。以下为待核验的数据类别与管理能力示例，最终以实际存储机制为准：

| 数据类型 | 管理功能 |
| -------- | -------- |
| 对话记录 | 查看存储信息、删除记录 |
| 定时任务 | 查看任务数据及执行历史 |
| 简报数据 | 查看缓存与历史简报 |
| 安全活动 | 查看记录及保留情况 |
| 临时文件 | 查看占用空间、清理 |

对于每类数据，应尽可能展示：

- 数据存储位置。
- 数据占用空间。
- 数据保留方式。
- 支持的清理操作。

所有信息必须来自实际数据存储机制，不得使用虚构的存储路径、容量或保留期限。

##### 2. 数据清理

支持清理适合由用户管理的本地数据，例如：

- 清理临时文件。
- 删除指定对话记录。
- 删除历史简报。
- 清理可以安全删除的缓存。

清理操作需要明确说明影响范围。对于不可恢复的删除操作，必须要求用户确认。

不得将清理缓存与删除原始数据混为一谈，也不得未经用户确认删除外部服务中的数据。

##### 3. 外部数据传输说明

让用户了解 Stella 在使用 AI 模型或外部服务时，哪些类型的信息可能被发送到外部。以下内容为说明示例，最终应根据实际请求流程核验：

| 服务 | 可能传输的数据 |
| ---- | -------------- |
| AI 模型 API | 对话内容、必要的工具结果及上下文 |
| GitHub | 用户授权范围内的仓库请求数据 |
| 邮箱服务 | 邮件查询与读取所需的数据 |
| 日历服务 | 日历查询与同步所需的数据 |

具体内容应根据 Stella 实际的请求流程展示，不应将所有潜在数据类型都标记为已经传输。

涉及敏感数据时，应避免在页面中直接展示完整内容。

##### 4. 隐私相关设置

集中展示现有的数据管理和隐私配置，可以包括：

- 对话记录保存方式。
- 历史数据保留策略。
- 临时文件清理。
- 外部服务数据访问情况。
- 数据导出与删除。

优先复用 Stella 已有的数据管理能力，不重复实现同一功能。

新增设置必须能够实际影响数据处理行为，不能仅提供没有后端支持的界面开关。

##### 5. 数据安全

所有数据与隐私管理操作都必须遵守以下要求：

1. 不显示 API Key、访问令牌和密码原文。
2. 不允许未经确认的大范围数据删除。
3. 不得通过普通数据清理操作破坏 Stella 必需的系统配置。
4. 数据删除后，相关界面和存储状态必须一致。
5. 对执行失败的清理操作明确提示原因。
6. 保护不同用户及对话之间的私有数据边界。

#### 验收标准

用户能够在安全中心了解 Stella 保存了哪些数据、数据存储在哪里、可能与哪些外部服务交换信息，并能够安全地管理或删除支持清理的数据。展示信息来自真实存储和请求流程，清理范围明确，不可恢复的删除需确认，失败原因可见。

---

## 三、安全中心目标结构与功能边界

完成上述问题修复和功能新增后，安全中心采用七个页面：

| 页面 | 核心职责 |
| ---- | -------- |
| 总览 | 默认权限、外部连接、凭据等核心配置概览 |
| 权限管理 | 默认权限、项目权限、对话权限 |
| 后台任务权限（新增） | 后台任务执行权限、权限来源、无人值守授权 |
| 外部连接 | 服务连接状态、授权范围及撤销 |
| 凭据 | 已配置凭据、来源及删除 |
| 安全活动 | 历史操作、授权与拒绝记录 |
| 数据与隐私（新增） | 本地数据、外部数据传输、数据保留与清理 |

两个新增功能遵循以下原则：

- 「后台任务权限」不重新实现定时任务管理。
- 「数据与隐私」不重新实现凭据或外部连接管理。
- 复用 Stella 现有的权限校验、任务调度、数据存储和安全审计能力，只补充用户需要的查看、控制和管理功能。
- 问题修复与功能新增中涉及同一数据、接口或权限规则的内容共同实现，避免重复功能和不必要的架构复杂度。
